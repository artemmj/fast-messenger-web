# Руководство по проекту

Документ фиксирует фактическое устройство frontend-клиента и предлагает приоритеты дальнейшей работы. Перечень возможностей описывает код этого репозитория, а не гарантии backend. Перед реализацией серверозависимых функций выясняйте у владельцев backend endpoint, формат запросов и ответов, авторизацию, ошибки и семантику событий.

## Назначение и текущий статус

Быстромессенджер — одностраничный веб-клиент для личных и групповых переписок. Реализованы регистрация и авторизация, защищённая оболочка, список чатов, загрузка последней страницы истории, отправка текста, получение WebSocket-событий, профиль и выход. Приложение использует Vue 3, Pinia, Vue Router, Axios и Vite; язык интерфейса — русский, тема — тёмная.

Клиент разделён на интерфейс, Pinia stores и API-модули. Desktop layout показывает список чатов рядом с активным содержимым; на ширине до 700 px мобильные маршруты переключают список, переписку и профиль в одну колонку.

## Архитектура и расположение кода

```text
src/
├── api/                 # Axios-клиент и вызовы auth/users/chats
├── assets/main.css      # тема, компоненты и responsive layout
├── components/
│   ├── chat/            # список чатов, поле ввода
│   └── ui/              # toast-компоненты
├── composables/         # маска телефона, Escape
├── layouts/MainLayout.vue # основная оболочка и текущее WS-соединение
├── router/index.js      # маршруты и проверка авторизации
├── services/chat-socket.js # альтернативный WS-клиент; сейчас не подключён
├── stores/              # auth, chats, messages, toast
├── utils/               # JWT payload, форматирование телефона
└── views/               # login, register, chats, chat, profile
```

- `src/main.js` создаёт Vue-приложение, Pinia и Router.
- `src/router/index.js` задаёт публичные `/login` и `/register` и защищённую оболочку `/` с маршрутами `/chats`, `/chats/:id`, `/profile`.
- `src/api/http.js` задаёт Axios timeout 15 секунд, добавляет сохранённый токен в `Authorization` и перенаправляет на `/login` при HTTP 401. Интерцептор самостоятельно удаляет токен и session ID из localStorage, но не синхронизирует все поля auth store.
- `src/stores/auth.js` хранит в Pinia токен, ID сессии и пользователя. Токен, session ID и JSON пользователя сохраняются в `localStorage` под ключами `access_token`, `session_id`, `user`.
- `src/stores/chats.js` хранит список, состояние загрузки, активный чат и локальные счётчики непрочитанных. `applySignal` меняет текст последнего сообщения, поднимает чат в списке и увеличивает счётчик, если событие не от текущего пользователя и чат не активен.
- `src/stores/messages.js` хранит историю по ID чатов, добавляет локальный `pending` пузырь и отправляет текст через REST. Ответ REST согласуется с `new_message` по серверному ID, в том числе когда WebSocket-событие пришло раньше HTTP-ответа.
- `src/assets/main.css` содержит общие стили и мобильный breakpoint. На мобильных устройствах `MainLayout` скрывает соседнюю колонку в зависимости от текущего маршрута; кнопка закрытия переписки/профиля возвращает к списку чатов.

## Текущие API-потоки

### Авторизация и профиль

- Вход: `POST /auth/login`; ожидаются `access_token` и `session_id`.
- Регистрация: `POST /users/register`; клиент ожидает токены и пользователя в ответе.
- Загрузка пользователя: `GET /users/{id}`. ID берётся из сохранённого пользователя или payload JWT (`user_id`).
- Изменение профиля: `PATCH /users/{id}`; UI отправляет email и/или пароль.
- Выход очищает локальные auth-данные через `auth.logout()`.

Форматы выше отражают ожидания клиентского кода. Перед изменением API-интеграции проверьте реальный backend-контракт. Не добавляйте автоматическое обновление токена без поддерживаемого сервером механизма.

### Чаты и сообщения

- Список: `GET /chats`; результат кэшируется в chats store до принудительной загрузки.
- Переписка: `GET /chats/{id}/get_messages`; API-клиент передаёт `limit=50`, `offset=0` по умолчанию.
- На текущем экране загружается только первая страница. API принимает параметры пагинации, но интерфейс пока не подгружает старые страницы при прокрутке.
- Отправка: `POST /chats/{id}/send_message` с телом `{ text }`. UI сначала рисует локальное сообщение. После ответа REST локальная запись получает серверный ID; при неудаче она получает `status: 'failed'`.
- Сейчас в шаблоне сообщения не используют `pending`/`failed` как CSS-классы и нет доступной кнопки повтора. Метод `retryMessage` в store есть, но интерфейс его не вызывает.

### WebSocket

Подключённое соединение создаётся в `src/layouts/MainLayout.vue` при монтировании защищённой оболочки по URL `/ws/chats?token=...` на host, выведенном из `VITE_API_BASE_URL`.

Ожидаемые формы событий, используемые клиентом:

```json
{"event":"new_message","chat_id":"...","data":{"id":"...","user_id":"...","text":"...","created_at":"..."}}
{"event":"chat_signal","chat_id":"...","data":{"last_message_text":"...","last_message_time":"...","sender_id":"..."}}
```

- `new_message` добавляет полноценное сообщение в messages store; повтор того же серверного ID игнорируется.
- `chat_signal` обновляет превью и локальный порядок чатов; не добавляет второе сообщение в историю. Свой сигнал и сигнал активного чата не увеличивают локальный unread count.
- Реальная отправка остаётся REST-запросом. Доставка события другим участникам после этого запроса зависит от backend и должна подтверждаться серверной реализацией.
- Активное WebSocket-соединение в `MainLayout.vue` не переподключается автоматически после обрыва. `src/services/chat-socket.js` содержит альтернативную логику, но сейчас не импортируется и не запускается. Не поддерживайте параллельно два подключения; при доработке выберите один клиент и удалите или интегрируйте второй.
- `chat_signal` содержит краткое превью, а не серверный ID сообщения. Не используйте его как полноценное сообщение истории: авторитетным событием для истории является `new_message`.
- Счётчики непрочитанных существуют только в оперативном состоянии клиента; подтверждённого серверного read receipt нет.

## Подтверждённые возможности интерфейса

- Регистрация и вход по телефону/паролю, локальное сохранение сессии, загрузка пользователя.
- Защищённые маршруты, отображение списка личных и групповых чатов.
- Названия личного чата на основе телефона собеседника; название группы и краткая информация о составе/администраторе.
- Загрузка последней страницы переписки, оптимистическая отправка текста и realtime-добавление полученных сообщений.
- Локальное обновление превью, порядка чата и unread-счётчика по `chat_signal`.
- Просмотр профиля, изменение email/пароля и выход.
- Мобильная компоновка списка, чата, профиля и auth-форм; учёт safe-area inset для переписки.

Не считать реализованными только на основании наличия заготовок: загрузку старых страниц в UI, retry отправки, reconnect сокета, серверные статусы прочтения, создание чатов/поиск пользователей, вложения, редактирование и удаление сообщений.

## Приоритеты дальнейшей работы

### P1 — надёжность существующих сценариев

1. Добавить автоматизированные проверки auth, отображения состояния отправки, дедупликации HTTP/WebSocket, собственного `chat_signal`, unread для активного/неактивного чата и маршрутизации на мобильном layout.
2. Вывести `pending`/`failed` в интерфейс, добавить доступный retry только для неудачного сообщения и убедиться, что переход от оптимистической записи к серверной не теряет и не дублирует сообщение.
3. Свести обработку 401/logout к единому способу очистки localStorage и Pinia, не создавая циклическую зависимость API-клиента от store.
4. Добавить корректное переподключение WebSocket, защиту от повторных подключений, обработку закрытия при logout и видимое состояние соединения.
5. Не терять WebSocket-события при параллельной загрузке/замене истории; тестировать гонки загрузки, события и HTTP-подтверждения.

### P2 — полнота переписки и интерфейса

1. Реализовать подгрузку старых страниц с сохранением позиции прокрутки и объединением по серверному ID.
2. Стилизовать unread badge и проверить, что события от своего пользователя не помечаются как непрочитанные, включая групповые чаты.
3. Добавить понятные состояния ошибки и retry для истории, списка чатов и профиля; не проглатывать сетевые причины в store там, где UI может их показать.
4. Проверить responsive поведение на узких экранах, виртуальной клавиатуре, landscape и устройствах с вырезами; проверить клавиатурную доступность и screen reader.
5. Настроить lint/test scripts и CI для тестов и production-сборки, документировать команды.

### P3 — функции, зависящие от backend

После подтверждения API-контракта можно проектировать создание личных/групповых чатов, поиск, управление участниками, read receipts, уведомления, вложения и операции над сообщениями. До подтверждения не добавлять UI, который обещает эти возможности.

## Правила изменений

- Сохраняйте разделение: HTTP в `src/api`, состояние/бизнес-логика в Pinia, представление в views/components.
- Следуйте текущему Vue Composition API и `<script setup>`; не вводите новую архитектуру без необходимости.
- Перед изменением серверозависимого поведения выясняйте контракт endpoint, payload, ответов, авторизации, ошибок и событий.
- WebSocket `new_message` — сообщение для истории; `chat_signal` — только обновление списка. Не добавляйте оба события в историю.
- Учитывайте типы/форматы ID: серверные ID сравнивайте согласованно, не полагаясь без проверки на строковый или числовой тип.
- Не храните bearer-токен в другом месте и не меняйте его модель хранения без согласования стратегии с backend-владельцами.
- Избегайте широких `catch` без логирования/передачи причины, если ошибка должна быть доступна пользователю или вызывающему коду.
- `src/stores/counter.js` — неиспользуемый starter-store; удалять только после проверки ссылок.

## Локальная разработка и проверки

Требуется Node.js `^22.18.0` или `>=24.12.0`.

```sh
npm install
cp .env.example .env
npm run dev
```

`VITE_API_BASE_URL` задаёт HTTP API и используется при построении WebSocket URL; пример — `http://localhost:8000`.

```sh
npm run build
npm run preview
```

В `package.json` пока нет test- и lint-команд. После добавления инфраструктуры обновите этот раздел и README. После визуальных изменений проверяйте как минимум мобильную ширину около 360 px и desktop layout.
