# Руководство по проекту

Этот файл описывает текущее устройство клиента и рекомендуемый порядок дальнейшей разработки. Пункты в плане — предложения по итогам анализа существующего кода, а не подтверждённые требования продукта. Перед реализацией функций, зависящих от сервера, сначала уточняйте доступные endpoint-ы, схемы запросов/ответов и правила авторизации backend API.

## Текущие решения

### Технологии и организация

- Vue 3 с Composition API и `<script setup>`, сборка через Vite, проект использует ES modules и JavaScript.
- Pinia хранит состояние авторизации (`src/stores/auth.js`), списка чатов (`src/stores/chats.js`) и истории сообщений (`src/stores/messages.js`).
- Vue Router разделяет публичные `/login` и `/register` и защищённую оболочку `/` с маршрутами `/chats`, `/chats/:id` и `/profile`. Основной layout монтирует список чатов рядом с содержимым маршрута.
- HTTP-вызовы вынесены в `src/api/`; общий Axios-клиент в `src/api/http.js` задаёт базовый URL, таймаут 15 секунд и заголовок авторизации.
- Общие CSS-переменные и стили находятся в `src/assets/main.css`; приложение оформлено тёмной темой.

### Авторизация и пользователь

- Вход: `POST /auth/login`; регистрация: `POST /users/register`. Ожидается ответ с `access_token` и `session_id`; регистрация также сохраняет пользователя из ответа.
- Токен, идентификатор сессии и данные пользователя хранятся в `localStorage` под ключами `access_token`, `session_id` и `user`. При запуске пользователь повторно загружается через `GET /users/{id}`; ID берётся из сохранённого пользователя или поля `user_id` в payload JWT.
- Профиль читает и изменяет пользователя через `GET /users/{id}` и `PATCH /users/{id}`. Изменяемые поля сейчас — email и пароль.
- Телефон форматируется на клиенте российской маской `+7(...)...`; форматирование отображения вынесено в `src/utils/format.js`.
- Перед изменением auth-кода учитывайте, что HTTP-интерцептор при `401` чистит токен и session ID в `localStorage` и перенаправляет на `/login`, но не синхронизирует напрямую Pinia-состояние и сохранённый ключ пользователя. Согласуйте единый способ завершения сессии, не создавая циклическую зависимость между API-клиентом и store.

### Чаты и сообщения

- Список чатов загружается `GET /chats` и кэшируется в `chats` store до принудительного обновления. Личные названия выводятся из телефона собеседника, групповые — из `name`; подзаголовок группы содержит число участников и отметку администратора.
- История загружается через `GET /chats/{id}/get_messages` с `limit=50` и `offset`. Backend выбирает страницу начиная с новых сообщений, но возвращает сообщения внутри страницы в хронологическом порядке; клиент показывает последнюю страницу первой и запрашивает старые страницы с растущим offset при прокрутке вверх. После добавления страницы клиент сохраняет видимую позицию и объединяет сообщения по ID.
- Отправка использует `POST /chats/{id}/send_message` с `{ text }`: store сначала добавляет локальное сообщение, затем заменяет его ответом сервера или помечает неудачную отправку как `failed`. Есть метод повтора неудачной отправки и заготовка дедупликации по ID для будущей доставки событий.
- Реального времени, сокетного соединения, API создания чата и списка поиска пользователей в текущем клиенте нет. Не предполагайте наличие соответствующих backend-функций без проверки API.
- Повторная загрузка первой страницы и предыдущих страниц истории доступен отдельно. UX повторной отправки сообщений всё ещё требует доработки: статусы `pending`/`failed` не привязаны к CSS-классам сообщения в шаблоне, а доступная пользователю кнопка повторной отправки не реализована.

## Рекомендуемая последовательность

### Первая очередь: надёжность уже реализованных сценариев

1. Доработать состояния отправки сообщений: показывать `pending`/`failed` в интерфейсе и предоставить повторную отправку только для неудачных сообщений.
2. Согласовать обработку `401` и logout: единообразно очищать токен, сессию, пользователя и Pinia-состояние, исключить оставшийся профиль после завершения сессии. Не вводить автоматическое обновление токена, пока серверный API этого не поддерживает.
3. Улучшить загрузку данных и ошибки: не скрывать причины ошибок сетевых запросов в store, показывать понятное состояние пользователю и предоставлять корректный retry для чатов, профиля и истории.
4. Добавить базовые автоматизированные проверки важных сценариев: формат телефона и валидацию формы, защиту маршрутов, сохранение/очистку auth-состояния, сортировку и пагинацию истории, оптимистичную отправку, обработку ошибки и повтор.

Сохраняйте текущую структуру — API в `src/api`, бизнес-состояние в Pinia, интерфейс в views/components. Тестовую и линтерную инфраструктуру следует добавить как часть этой очереди, выбрав инструменты, совместимые с текущими версиями Vue и Vite; сейчас соответствующих команд в `package.json` нет.

### Вторая очередь: завершение основных сценариев общения

1. После подтверждения API-контракта реализовать создание личных и групповых чатов и необходимые действия с участниками. Отразить успешное создание в `chats` store и корректно обновлять список после изменений.
2. Если backend предоставляет WebSocket или SSE, подключить доставку сообщений в `messages` store: дедупликация по серверному ID, согласование серверного подтверждения с оптимистичной записью, обработка отключения/повторного соединения и освобождение подписки при смене чата.
3. Если сервер поддерживает эти возможности, дополнить интерфейс непрочитанными сообщениями и обновлением краткой информации в списке чатов.
4. Добавить соответствующие интеграционные проверки на API-контракт и конкурирующие сценарии (например, событие сокета до HTTP-подтверждения отправки).

Не реализуйте UI, который обещает неподдерживаемое сервером поведение; сначала зафиксируйте контракт API и состояния ошибок/пустых результатов.

### На будущее

- Поиск чатов и пользователей, непрочитанные счётчики, отметки доставки/прочтения и уведомления — при наличии поддержки на сервере.
- Вложения, редактирование и удаление сообщений, управление участниками и настройка групп — после определения требований и API.
- Адаптивная мобильная раскладка, доступность клавиатурой и screen reader, локализация и более полная обработка часовых поясов.
- CI для тестов, линтинга и production-сборки; документирование контракта API и сценариев развёртывания.
- Удалить неиспользуемый starter-store `src/stores/counter.js`, если он не понадобится; заменить шаблонные `<title>` и пустой `lang` в `index.html`.
- Пересмотреть хранение bearer-токена в `localStorage` вместе с backend-владельцами, оценив модель угроз и доступные серверные механизмы сессии. Не менять способ хранения токенов отдельно от согласованной стратегии безопасности.

## Локальная разработка

```sh
npm install
cp .env.example .env
npm run dev
```

`VITE_API_BASE_URL` задаёт базовый адрес backend API; `.env.example` содержит `http://localhost:8000`. Используйте `npm run build` для production-сборки и `npm run preview` для её локального просмотра. В репозитории пока нет test/lint scripts; при их добавлении документируйте команды здесь и запускайте подходящие проверки для изменённого поведения.
